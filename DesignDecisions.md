# TaskTracker Design Decisions

TaskTracker is packaged as a lightweight FastAPI service with PostgreSQL support and is deployable through Docker Compose or Kubernetes. The design prioritizes reproducibility, security, and predictable operation over maximum infrastructure complexity.

The application image uses `python:3.11-slim-bookworm` rather than the floating `python:3.11-slim` tag. Bookworm provides a smaller Debian-based runtime while retaining a mature security-patch history. The image is pinned to the Bookworm variant because newer Debian releases had unresolved high-severity vulnerabilities during scanning. Pinning the distribution also makes builds more predictable than relying on a tag whose underlying operating-system release may change over time.

The Dockerfile uses a two-stage build. The first stage creates a virtual environment and installs only the application’s runtime dependencies. The second stage contains the minimal runtime environment and copies in the virtual environment, application code, templates, model files, and version metadata. Training code, tests, datasets, and development tooling are excluded through both the multi-stage build and `.dockerignore`. This keeps the production image smaller and reduces its attack surface. The image also upgrades the virtual environment’s packaging tools and applies available operating-system security updates during the build.

The container runs as a dedicated non-root `app` user. This limits the potential impact of a container compromise and avoids giving the web process unnecessary filesystem privileges. Python is configured not to create bytecode files, and output is unbuffered so logs are visible immediately to Docker and Kubernetes logging systems. The service listens on port `8000` and exposes a `/health` endpoint used by container and orchestration health checks.

Model training is intentionally kept outside the image build. CI trains the model, evaluates it against the project’s F1 and ROC-AUC quality thresholds, runs the tests, and publishes the resulting `model.pkl` and `metrics.json` as an artifact. The CD workflow then builds the image using that exact artifact. This prevents Docker builds from retraining the model unpredictably and ensures that the model tested in CI is the model packaged for deployment. The image is scanned with Trivy before it is pushed, and production promotion requires manual approval.

For local development, Docker Compose provides two services: the FastAPI application and PostgreSQL 16 Alpine. PostgreSQL uses a named volume so local data survives container restarts. Both services share a private bridge network, and the application waits for the database health check before starting. The database is included to mirror the Kubernetes topology and to allow the complete stack to be exercised locally, even though the current prediction endpoints do not yet persist application data.

In Kubernetes, the application runs as two replicas behind a ClusterIP Service. Two replicas provide basic availability during rolling updates and allow the service to continue responding if one pod is unavailable. The deployment uses a rolling-update strategy with `maxUnavailable: 0`, so existing capacity is retained while a replacement pod starts. PostgreSQL is deployed separately as a single-replica StatefulSet with a persistent volume claim. This reflects the database’s stateful nature and ensures data is stored outside the container lifecycle.

The application and database each request `250m` CPU and `256Mi` memory, with limits of `500m` CPU and `512Mi` memory. These values are conservative starting points for a lightweight Python API that loads a small scikit-learn model, while still allowing short periods of increased demand. The limits prevent an individual pod from consuming unlimited cluster resources, and the requests give the scheduler a predictable baseline for placement. They should be revisited using production CPU and memory measurements as traffic grows.

Finally, Kubernetes liveness and readiness probes call the application’s `/health` endpoint, while PostgreSQL uses `pg_isready`. Readiness checks prevent traffic from reaching pods that have not initialized successfully; liveness checks allow Kubernetes to restart an unhealthy process. Configuration is separated into ConfigMaps and Secrets, although the checked-in secret values are demonstration values only and must be replaced through a proper secret-management process in production.
